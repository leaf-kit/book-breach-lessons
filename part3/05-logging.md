# 3.5 로그 설계

로그 설계의 출발점이 이 장면입니다.
**75센트가 보였기 때문에 추적이 시작됐습니다.**
기록이 없었으면 불일치도 없었고 추적도 없었습니다.

## 없으면 아무것도 못 합니다

2025년 통신사 침해 조사에서 조사단 내부에서 이런 지적이 나왔습니다.
2024년 이전 기간은 로그가 1년 치도 남아 있지 않아
**유출 여부를 확인할 방법 자체가 없다**는 것이었습니다(⚠️ F-023).

최초 감염은 2021년 8월로 확인됐습니다(✅ F-020).
그 사이 3년 동안 무엇이 나갔는지는 영원히 모릅니다.

이것이 로그의 값입니다. 로그는 공격을 막지 않습니다.
**무슨 일이 있었는지 아는 유일한 방법**입니다.
모르면 통지도 못 하고 보상 범위도 못 정하고 재발 방지도 못 합니다.

## 목적이 네 개입니다

로그를 하나로 묶으면 전부 애매해집니다. 목적마다 요구가 다릅니다.

| 목적 | 누가 보나 | 보관 | 요구사항 |
|---|---|---|---|
| 탐지 | 보안 담당 | 짧게, 뜨겁게 | 빨리 검색됨 |
| 감사 | 감사, 규제 | 길게 | 변조 불가, 완전성 |
| 포렌식 | 조사자 | 길게, 차갑게 | 원본성, 시간 정확도 |
| 디버깅 | 개발자 | 아주 짧게 | 상세함 |

**가장 자주 섞이는 것이 감사와 디버깅입니다.**
디버깅 로그는 상세해야 해서 개인정보가 들어갑니다. 감사 로그는 오래 둬야 합니다.
둘을 섞으면 개인정보가 오래 남습니다. 그게 사고가 됩니다.

디버깅 로그는 짧게 두고 지웁니다. 하루나 이틀이면 충분합니다.

## 반드시 남길 것

아래가 없으면 사고 때 재구성이 안 됩니다.

**인증** — 로그인 성공과 실패, 로그아웃, 비밀번호 변경, 다중 인증 등록과 해제

**권한** — 권한 부여와 회수, 역할 변경, 관리자 작업

**접근** — 누가 언제 어떤 자원에 접근했는지. 특히 개인정보 조회

**변경** — 설정 변경, 데이터 대량 변경, 삭제

**계정 생애주기** — 생성, 비활성화, 삭제, 외부 연동 추가

**관리 세션** — 서버 접속, 실행한 명령

세 번째가 법령에서 말하는 접속기록입니다. 조회 로그가 없으면
"무엇이 나갔는가"를 못 셉니다. 2026년 금융권 사건에서 은행마다
유출 건수를 숫자로 말할 수 있었던 것은 조회 로그가 있었기 때문입니다.

## 절대 남기지 말 것

| 남기지 않는 것 | 대신 |
|---|---|
| 비밀번호 (평문이든 해시든) | 아무것도 안 남깁니다 |
| 인증 토큰, API 키, 세션 ID 전체 | 앞 6자리 정도만 |
| 주민등록번호, 카드번호 전체 | 마스킹하거나 식별자로 대체 |
| 요청 본문 전체 | 필요한 필드만 골라서 |
| 응답 본문 전체 | 상태 코드와 건수만 |

```python
# 나쁜 예 — 요청을 통째로 찍는다
log.info("payment", extra={"request": request.json()})
```

```python
# 좋은 예 — 추적에 필요한 것만 찍는다
log.info("payment", extra={
    "order_id": order.id,
    "amount": order.amount,
    "card_last4": card.number[-4:],
    "trace_id": ctx.trace_id,
})
```

실수로 들어가는 것을 막으려면 **출력 단계에 마스킹 필터**를 둡니다.
사람이 매번 조심하는 방식은 실패합니다.

## 양을 줄이는 법

로그는 비쌉니다. 저장도 비싸고 검색도 비쌉니다.
그래서 "다 남기자"는 현실적이지 않고, "줄이자"가 "안 남기자"가 되기 쉽습니다.

**이벤트 중심으로 남깁니다.** 함수가 호출될 때마다 찍지 않고
의미 있는 사건이 일어날 때 찍습니다. "주문 생성됨", "권한 변경됨" 같은 것입니다.

**계층을 나눕니다.** 최근 것은 빠른 저장소에, 오래된 것은 싼 저장소에 둡니다.
감사와 포렌식용은 느려도 됩니다.

**디버그만 표본으로 남깁니다.** 전부가 아니라 일부만 상세히 남겨도
디버깅에는 대개 됩니다. 비율은 서비스 성격에 따라 정하십시오.
**감사와 접근 로그는 표본을 쓰지 않습니다.** 빠진 한 건이 조사의 공백이 됩니다.

**중복을 없앱니다.** 같은 요청이 계층마다 찍히는 경우가 흔합니다.
상관 ID 를 두고 한 곳에서만 찍습니다.

## 품질 요건

남기기만 하면 안 됩니다. 쓸 수 있어야 합니다.

**구조화합니다.** 문자열을 이어 붙인 로그는 검색이 안 됩니다.
키와 값으로 남깁니다.

**상관 ID 를 둡니다.** 요청 하나가 여러 서비스를 거칠 때
같은 ID 로 묶여야 추적이 됩니다. 이것이 없으면 분산 환경에서 조사가 불가능합니다.

**시간을 맞춥니다.** 서버마다 시계가 다르면 순서를 못 정합니다.
UTC 로 통일하고 시각 동기화를 겁니다. 사고 조사에서 1초 차이가 중요할 때가 있습니다.

**서버 밖으로 보냅니다.** 공격자가 서버를 장악하면 그 서버의 로그부터 지웁니다.
**같은 서버에만 있는 로그는 사고 때 없는 로그입니다.**

**변조를 막습니다.** 쓰기만 가능하고 수정과 삭제가 안 되는 저장소에 둡니다.

**접근을 통제합니다.** 로그에는 민감한 정보가 모입니다.
로그 조회 자체를 권한으로 관리하고, 누가 로그를 봤는지도 남깁니다.

**로그 주입을 막습니다.** 사용자 입력에 줄바꿈이 들어가면
가짜 로그 줄을 만들 수 있습니다. 구조화된 형식을 쓰면 대부분 해결됩니다.

## 보관 기간

| 종류 | 권장 | 근거 |
|---|---|---|
| 디버그 | 1~2일 | 개인정보가 섞일 수 있습니다 |
| 애플리케이션 | 30~90일 | 운영 분석 |
| 인증과 권한 | 1년 이상 | 장기 잠복 대응 |
| 접근기록 | 1년 이상 | 장기 잠복 대응. **법정 기간은 아래 참조** |
| 관리 세션 | 1년 이상 | 사고 조사 |

**위 표는 이 책의 기술적 권장입니다. 법정 요건이 아닙니다.**

접속기록의 **법정 보관 기간과 점검 주기는 고시가 정합니다.**
이 책은 그 숫자를 적지 않습니다. 관련 고시의 개정 시행일이 자료마다
2026-10-30 과 10-31 로 갈리고, 점검 주기 완화가 그 날짜에 걸려 있어서
**하루 차이가 위반 여부를 가르기 때문**입니다. 틀린 숫자를 적는 것보다
안 적는 쪽이 낫습니다.

[국가법령정보센터 행정규칙](https://www.law.go.kr/LSW/admRulLsInfoP.do) 에서
「개인정보의 안전성 확보조치 기준」을 열고,
**본문이 아니라 부칙**을 보십시오. 유예 항목이 거기 있습니다.

확인하고 나면 **기술적 권장과 법정 요건 중 더 긴 쪽**을 따릅니다.
대개 기술적 권장이 더 깁니다. 법은 최소선이지 목표가 아닙니다.

## 로그 정책 템플릿

문서로 만들어 둡니다. 없으면 개발자마다 다르게 찍습니다.

```yaml
# 로그 정책
형식: JSON 구조화
시간: UTC, ISO 8601
필수 필드: [timestamp, level, service, trace_id, actor, action, result]

남긴다:
  - 인증: 로그인 성공과 실패, 로그아웃, 비밀번호 변경, MFA 변경
  - 권한: 부여, 회수, 역할 변경, 관리자 작업
  - 접근: 개인정보 조회 (대상 건수 포함, 내용 제외)
  - 변경: 설정, 대량 변경, 삭제
  - 계정: 생성, 비활성화, 삭제

남기지 않는다:
  - 비밀번호, 토큰 전체, 세션 ID 전체
  - 주민등록번호, 카드번호 전체
  - 요청과 응답 본문 전체

보관:
  debug: 2일
  app: 90일
  auth: 1년
  access: 법정 기간 이상
  admin_session: 1년

전송: 생성 즉시 중앙 수집기로. 로컬에만 두지 않는다
변조 방지: 쓰기 전용 저장소
접근 통제: 로그 조회 권한 분리, 조회 이력 기록
```

> ### 금융권 사건에 적용하면
>
> 2026년 사건에서 각 은행은 유출 건수를 숫자로 발표했습니다.
> 신한은행 25,729명 같은 식입니다(⚠️ F-003).
>
> 이 숫자가 나올 수 있었다는 것은 **조회 로그가 있었다**는 뜻입니다.
> 누가 어떤 고객 정보를 몇 건 조회했는지 남아 있지 않으면
> 저 숫자를 만들 수 없습니다.
>
> 통신사 사건과 대비됩니다. 거기서는 로그가 없어 확인할 방법이 없었습니다(⚠️ F-023).
> **같은 피해를 당해도 로그가 있으면 범위를 말할 수 있고, 없으면 말할 수 없습니다.**
> 말할 수 없으면 최악을 가정해야 하고, 그게 더 큰 비용입니다.

## 체크리스트

- [ ] 3개월 전 접근 기록을 검색할 수 있다
- [ ] 로그가 생성 즉시 서버 밖으로 전송된다
- [ ] 로그에 비밀번호, 토큰 전체, 주민등록번호가 없다
- [ ] 출력 단계에 마스킹 필터가 있다
- [ ] 로그가 구조화되어 있고 상관 ID 가 있다
- [ ] 모든 서버의 시각이 동기화되어 있다
- [ ] 로그 저장소가 수정과 삭제를 막는다
- [ ] 로그 조회에 권한이 걸려 있고 조회 이력이 남는다
- [ ] 로그 정책이 문서로 있다
- [ ] 보관 기간이 법정 요건 이상이다

## 이해 점검

1. 로그가 공격을 막지 못하는데도 가장 먼저 챙겨야 하는 이유는 무엇입니까.
2. 감사 로그와 디버그 로그를 섞으면 무엇이 문제입니까.
3. 로그를 서버 밖으로 보내야 하는 이유는 무엇입니까.
4. 상관 ID 가 없으면 분산 환경에서 무엇을 못 합니까.
5. 유출 범위를 말할 수 없으면 왜 비용이 더 큽니까.
