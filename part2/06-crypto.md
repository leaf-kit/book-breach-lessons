## 직접 만들지 마십시오

이 장에서 가장 중요한 문장을 먼저 적습니다. **암호를 직접 만들지 않습니다.**
직접 만든다는 것에는 알고리즘을 설계하는 것뿐 아니라
표준 조각을 자기 방식으로 조합하는 것도 포함됩니다.

암호는 틀려도 동작합니다. 암호화한 결과가 나오고 복호화도 됩니다.
테스트도 통과합니다. 깨지는 것은 몇 년 뒤 누가 분석할 때입니다.
**틀린 것이 티가 안 나는 분야**라서 직접 만들면 안 됩니다.

검증된 라이브러리의 높은 수준 함수를 씁니다. 블록 암호 모드를 직접 고르고
초기화 벡터를 직접 다루는 코드가 보이면, 그 자리를 먼저 의심합니다.

## 네 가지 쓰임

암호는 네 가지 일을 합니다. 섞으면 잘못된 도구를 고릅니다.

| 쓰임 | 무엇을 보장하나 | 쓰는 것 |
|---|---|---|
| 기밀성 | 남이 못 읽는다 | 대칭 암호, 공개키 암호 |
| 무결성 | 바뀌지 않았다 | 해시, MAC |
| 인증 | 보낸 사람이 맞다 | MAC, 전자서명 |
| 부인 방지 | 보냈다는 것을 부정 못 한다 | 전자서명 |

가장 흔한 오해는 **암호화하면 무결성도 보장된다**는 것입니다.
아닙니다. 암호문을 조작해 복호화 결과를 바꾸는 공격이 있습니다.
요즘 라이브러리는 기밀성과 무결성을 함께 주는 방식을 기본으로 하는데,
옛 코드는 그렇지 않은 경우가 많습니다.

## 비밀번호 저장은 암호화가 아닙니다

비밀번호를 암호화해서 저장하면 안 됩니다. 암호화는 되돌릴 수 있기 때문입니다.
열쇠를 가진 사람은 전부 읽습니다.

비밀번호는 **되돌릴 수 없게** 저장합니다. 그리고 그냥 해시로도 부족합니다.
빠른 해시는 공격자도 빠르게 돌립니다. 비밀번호 전용으로 설계된,
느리게 만든 방식을 써야 합니다.

국내 요건은 비밀번호에 해시함수를 쓰고, 주민등록번호와 신용카드번호,
계좌번호, 여권번호, 운전면허번호, 외국인등록번호에는 블록암호를 쓰도록
안내합니다. SHA-1 은 비권고이고 SHA-2 계열이 권고입니다(⚠️ F-114).

**이 자리에서는 국내 안내와 국제 모범사례를 함께 보십시오.**
국내 안내 문서는 개정 주기가 길어서 현재 국제 권고와 차이가 날 수 있습니다.
이 책은 어느 알고리즘을 쓰라고 특정하지 않습니다. 특정하는 순간 낡기 때문입니다.

대신 **고르는 기준**을 드립니다.

- 비밀번호 **전용으로 설계된** 방식인가. 범용 해시를 쓰지 않습니다
- **느리게 만들 수 있는가.** 비용 인자를 조정할 수 있어야 합니다
- 공격자의 하드웨어 이점을 **줄이는 설계**인가
- 국내 요건과 국제 권고가 다르면 **더 보수적인 쪽**을 따릅니다

[KISA 암호이용활성화](https://seed.kisa.or.kr/) 의 안내서와
[OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)
를 나란히 놓고 위 네 기준으로 판단하십시오.

## 법적 최소 요건과 현재 모범 사례

이 둘은 다릅니다. 섞으면 "법은 지켰는데 안전하지 않은" 상태가 됩니다.

| | 법적 최소 요건 | 현재 모범 사례 |
|---|---|---|
| 근거 | 법령과 고시 | 국제 표준, 학계, OWASP |
| 바뀌는 속도 | 느리다 | 빠르다 |
| 안 지키면 | 제재 | 제재는 없다. 깨질 뿐이다 |
| 어디서 보나 | [국가법령정보센터](https://www.law.go.kr/), [KISA](https://seed.kisa.or.kr/) | [NIST](https://csrc.nist.gov/), [OWASP](https://owasp.org/), [IETF](https://www.ietf.org/) |

**둘 다 봐야 합니다.** 법적 요건만 보면 낡은 방식을 계속 쓰게 되고,
모범 사례만 보면 국내 요건을 빠뜨립니다.

국가와 공공기관은 추가 제약이 있습니다. 검증필 암호모듈을 써야 하고,
검증 대상 블록암호는 ARIA, SEED, LEA, HIGHT 입니다(⚠️ F-114).
민간이 이 목록을 그대로 따를 필요는 없습니다.

## 피해야 할 것

이유까지 알아야 다음에 비슷한 것을 만나도 판단할 수 있습니다.

| 피할 것 | 왜 |
|---|---|
| MD5, SHA-1 | 서로 다른 입력이 같은 결과를 내게 만들 수 있습니다 |
| DES, 3DES, RC4 | 키가 짧거나 구조적 약점이 알려졌습니다 |
| ECB 모드 | 같은 평문 블록이 같은 암호문이 되어 패턴이 드러납니다 |
| 무결성 없는 암호화 | 암호문 조작을 탐지하지 못합니다 |
| 자체 제작 난수 | 예측 가능하면 열쇠가 예측됩니다 |
| 하드코딩된 열쇠 | 1.3 의 비밀 관리를 보십시오 |

발견했을 때 당장 바꿀 수 없다면, **목록에 올리고 기한을 정하는 것**까지는 해야 합니다.
목록에 없으면 영원히 남습니다.

## 열쇠 관리가 암호의 전부입니다

알고리즘을 아무리 잘 골라도 열쇠가 평문으로 옆에 있으면 소용없습니다.
데이터베이스를 암호화하고 열쇠를 같은 서버에 두는 구성이 흔한데,
서버를 장악한 공격자에게는 암호화가 없는 것과 같습니다.

열쇠 관리에서 볼 것은 넷입니다.

**어디에 두나.** 별도의 열쇠 관리 서비스나 하드웨어 모듈에 둡니다.
최소한 데이터와 다른 권한 경계 안에 둡니다.

**누가 꺼낼 수 있나.** 열쇠에 접근할 수 있는 계정의 수가
암호화의 실제 강도입니다.

**얼마나 자주 바꾸나.** 교체 절차가 없으면 유출됐을 때 바꿀 수가 없습니다.
교체를 해 본 적 없는 체계는 사고 당일에 처음 해 보게 됩니다.

**봉투 암호화를 쓰나.** 데이터는 데이터 열쇠로 암호화하고,
데이터 열쇠는 상위 열쇠로 암호화합니다. 상위 열쇠 하나만 바꾸면
전체 데이터를 다시 암호화하지 않아도 됩니다.

## 양자내성암호, 왜 지금인가

양자 컴퓨터가 아직 없는데 암호를 바꾸는 이유는 하나입니다.
**수집 후 해독**입니다.

공격자가 지금 암호문을 모아 둡니다. 지금은 못 풉니다.
나중에 풀 수 있게 되면 그때 풉니다. 그러니까 **오늘 나간 데이터의 보호 기간**이
문제입니다. 10년 뒤에도 비밀이어야 하는 데이터는 지금 위험합니다.

의료 기록, 신원 정보, 장기 계약, 영업 비밀, 국가 기밀이 여기 해당합니다.
반대로 일주일 뒤면 가치가 없는 데이터는 급하지 않습니다.
**보존 기간이 우선순위를 정합니다.**

## 표준은 어디까지 왔나

NIST 는 2024년 8월 13일에 FIPS 203(ML-KEM, 키 설정), FIPS 204(ML-DSA, 전자서명),
FIPS 205(SLH-DSA, 해시 기반 서명)를 최종 확정했습니다(✅ F-110).
이 셋은 확정된 표준입니다.

예비 수단도 하나 더 골라 두었습니다. 2025년 3월 NIST IR 8545 에서
HQC 를 예비 키 설정 알고리즘으로 선정했습니다(⚠️ F-112).
같은 수학적 가정에 기대지 않는 두 번째 선택지를 두는 것인데,
**알고리즘 하나가 깨졌을 때를 대비하는 방식**입니다.
조직 차원에서도 같은 원리가 적용됩니다. 그게 아래의 암호 민첩성입니다.

전환 일정은 다릅니다. NIST IR 8547 은 2024년 11월 12일 공개된
**초안(Initial Public Draft)** 이고 2026년 중반 기준으로 여전히 초안입니다.
112비트 보안 강도의 양자 취약 공개키 알고리즘을 2030년 이후 사용 억제,
2035년 이후 금지하자고 제안합니다(⚠️ F-111).

**초안입니다.** 2030과 2035를 확정된 정책처럼 인용하지 마십시오.
다만 미 연방은 초안 상태에서도 그 일정을 계획 기준으로 삼고 있고,
행정명령과 예산 지침이 날짜를 따라가고 있습니다(⚠️ F-113).

한국은 2023년 7월 범국가 양자내성암호 전환 마스터플랜을 내고
2035년을 목표로 두었습니다. KpqC 4종(AIMer, HAETAE, NTRU+, SMAUG-T)이
2025년 1월 최종 선정됐습니다(✅ F-115).

## 지금 할 일

전환은 몇 년짜리 일입니다. 그런데 **첫 단계는 이번 분기에 할 수 있습니다.**

**1. 암호 자산 목록을 만듭니다.** 우리가 어디서 무슨 알고리즘을 쓰는지 적습니다.
TLS 설정, 데이터베이스 암호화, 서명, 토큰, VPN, 코드 서명, 하드웨어.

이 목록이 없으면 전환 계획을 세울 수 없습니다.
**지금 이 목록이 있습니까.** 없다면 그것이 1번인 이유입니다.

**2. 보존 기간이 긴 데이터를 찾습니다.** 10년 뒤에도 비밀이어야 하는 데이터가
어디 있는지 봅니다. 그것이 전환 1순위입니다.

**3. 암호 민첩성을 확보합니다.** 알고리즘을 바꾸려면 코드를 고쳐야 하는 구조인지,
설정만 바꾸면 되는 구조인지 봅니다. 전자라면 그것부터 고칩니다.
다음 전환은 양자 때문이 아니라 다른 이유로도 옵니다.

**4. 하이브리드를 검토합니다.** 기존 알고리즘과 새 알고리즘을 함께 써서
둘 다 깨져야 뚫리게 만드는 방식입니다. 전환기의 표준 접근입니다.

1번과 2번은 암호 지식이 없어도 됩니다. 목록을 만드는 일입니다.

> ### 금융권 사건에 적용하면
>
> 2026년 사건에서 유출된 항목에는 암호화된 주민등록번호가 포함됐습니다(⚠️ F-003).
>
> 암호화되어 있었다는 것은 좋은 소식입니다. 다만 두 가지를 더 물어야 합니다.
> 열쇠가 같은 환경에 있었는가, 그리고 어떤 알고리즘이었는가.
>
> **"암호화했습니다"는 답이 아니라 질문의 시작입니다.**
> 사고 보고서에서 이 두 질문에 답할 수 있는 조직이 실제로 암호화한 조직입니다.

## 우리 조직 적용표

| 지금 가능 | 3개월 내 | 투자 필요 |
|---|---|---|
| 암호 자산 목록 초안 만들기 | 보존 10년 이상 데이터 식별 | 열쇠 관리 서비스 도입 |
| MD5, SHA-1, 3DES 사용처 찾기 | 열쇠 저장 위치 점검 | 하드웨어 보안 모듈 |
| 열쇠 접근 계정 수 세기 | 암호 민첩성 평가 | 양자내성암호 시범 전환 |
| TLS 설정 확인 | 교체 절차 문서화 | 봉투 암호화 전환 |

## 체크리스트

- [ ] 암호 자산 목록이 있다
- [ ] MD5, SHA-1, DES, 3DES, RC4, ECB 사용처가 없거나 목록에 올라 있다
- [ ] 비밀번호가 되돌릴 수 없는 방식으로 저장된다
- [ ] 데이터베이스 암호화 열쇠가 데이터와 다른 권한 경계에 있다
- [ ] 열쇠 교체 절차가 있고 한 번 이상 실행해 봤다
- [ ] 보존 기간 10년 이상 데이터를 식별했다
- [ ] 알고리즘 교체가 설정 변경으로 가능한 구조다
- [ ] 암호를 직접 구현한 코드가 없다

## 이해 점검

1. 암호를 직접 만들면 안 되는 이유를 "틀려도 동작한다"로 설명해 보십시오.
2. 암호화와 무결성 보장은 왜 다릅니까.
3. 비밀번호를 암호화해서 저장하면 안 되는 이유는 무엇입니까.
4. 양자 컴퓨터가 없는데 지금 전환을 시작하는 이유는 무엇입니까.
5. NIST IR 8547 의 2030과 2035를 인용할 때 반드시 붙여야 하는 단서는 무엇입니까.

**2번.** 같이 털리면 암호화는 없던 일이 됩니다.
점검할 것은 **켜져 있는지**가 아니라 **열쇠가 어디 있는지**입니다.
암호의 전부가 열쇠 관리라고 말하는 이유가 이것입니다.

</details>
